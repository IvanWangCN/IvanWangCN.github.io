先讲一个真实场景。

你给公司搭了一个知识库问答，用户问“报销流程要几天”。系统检索回来三段话：一段讲“差旅报销标准”，一段讲“审批流程图说明”，一段讲“发票粘贴规范”。模型把这仨拼在一起，洋洋洒洒答了三百字，唯独没回答“几天”。用户骂了一句“人工智障”，你打开日志一看：真正写着“审核周期为5个工作日”的那段话，压根没被召回。

这就是RAG最典型的翻车方式——**不是模型不会答，是它没拿到该看的那页纸**。下面这张图是全链路的总览，后面每一节我都配一张小图和一个比喻，把每个环节“到底在干嘛、哪里容易断”讲清楚。

```
┌─────────────────────────── 离线（决定天花板） ───────────────────────────┐
│                                                                          │
│  原始文档 ──► 解析 ──► 清洗 ──► 分块 ──► 向量化 ──► 建索引              │
│  (PDF/Word)   版面     去噪    切块    变坐标     ANN+倒排+元数据        │
│                                                                          │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   │ 知识库
                                   ▼
┌─────────────────────────── 在线（受天花板约束） ─────────────────────────┐
│                                                                          │
│  用户问题 ──► 改写 ──► 多路召回 ──► 融合 ──► 重排序 ──► 拼Prompt ──► 生成│
│              HyDE     向量+BM25     RRF    cross-encoder   约束+拒答     │
│                                                                          │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   │
                                   ▼
                          评估闭环（定位断在哪层）
```

## 一、解析：先看清楚纸长什么样，再认字

**打个比方**：把一份PDF喂给程序，就像把一张报纸塞给一个只会从左到右逐字读的人。报纸有双栏、有表格、有页眉页脚，逐字读出来就是“今天天气央行宣布降准晴朗适合出游”——顺序全乱。

所以解析的第一件事不是OCR，是**版面分析**：先框出哪块是标题、哪块是正文、哪块是表格、哪块是页脚，再按人的阅读顺序重排。

```
双栏PDF原始版面：              正确阅读顺序：
┌─────────┬─────────┐         标题
│  标题   │         │         ↓
├─────────┼─────────┤         左栏正文 → 右栏正文
│ 左栏正文│ 右栏正文│         ↓
├─────────┼─────────┤         表格（整块保留）
│  表格   │  页脚   │         ↓
└─────────┴─────────┘         页脚（丢弃）
   ↑ 直接OCR = 左一行右一行交替，语义断裂
```

**坑在哪**：很多人图省事，PDF进来直接丢OCR。结果是标题层级没了、表格变成一坨乱码、双栏内容交错。这些结构信息一旦丢了，后面分块再怎么调都救不回来——你没法从一个已经搅碎的文档里切出语义完整的块。

## 二、分块：切蛋糕，别切在奶油花上

**打个比方**：分块就是把一本长文档切成一张张卡片，每张卡片要能独立看懂。切得好，一张卡片是一个完整的意思；切得烂，卡片上只有半句话。

看两个真实对比：

```
❌ 切在句子中间（固定200字硬切）：
卡片A: "...患者应在停药后90天内..."
卡片B: "...定期复查肝功能，90天后..."
       ↑ 卡片A的"90天内"到底干嘛？不知道。检索命中A也答不出。

✅ 切在语义边界：
卡片: "【停药随访】患者应在停药后90天内定期复查肝功能。
       90天后如无异常可延长至半年一次。"
       ↑ 一张卡片自带主语、条件、结论，能独立回答"停药后多久复查"。
```

**PPL（困惑度）在这里扮演什么角色**：PPL可以理解为“语言模型对下一个词的惊讶程度”。读到“今天天气很好，我们去公园___”，下一个词大概率是“散步”，模型不惊讶，PPL低；突然冒出“量子色动力学”，模型很惊讶，PPL飙升。

很多文章说“PPL飙升说明逻辑断层了”——**这话只对一半**。PPL飙升还可能是因为出现了生僻专有名词、文体从叙述变成引用、句子突然变长。它是个**候选信号**，不是判决书。正确用法是：PPL飙升处标为“疑似边界”，再让模型或规则复核一下，而不是看到峰值就一刀切下去。

**尺寸给个锚点**：通用文本从 **300–500 tokens** 起步，重叠 10%–15%。切到 100–200 tokens 会碎到没上下文，切到 1000+ tokens 会一张卡片塞三个主题。表格、代码、条款尽量整块保留，别在结构中间下刀。

## 三、向量化与索引：把文字变成坐标，再给坐标建目录

### 3.1 Embedding：文字 → 坐标

**打个比方**：Embedding 就是把每段话扔进一个几百维的坐标系里，意思相近的话坐标靠得近。“苹果手机续航好”和“iPhone电池耐用”会挨在一起，“苹果手机续航好”和“苹果派怎么做”会离得很远。

检索时，把用户问题也变成坐标，找坐标最近的那几段——这就是**向量检索**。

### 3.2 ANN索引：不是一本本翻，是按楼层找

**打个比方**：知识库有100万段，你不可能每次都和100万段逐一算距离。**ANN（近似最近邻）索引**就像图书馆的分区目录：先按大类分到几个区，再在区内细找。

以最常用的 **HNSW** 为例，它的结构像“高速公路 + 省道 + 小巷”三层路网：

```
Layer 2（高速）:  A ●────────────────● E          节点少、跨度大，先快速跳到大区域
Layer 1（省道）:  A ●──────● C ──────● E
Layer 0（小巷）:  A ●─● B ●─● C ●─● D ●─● E      节点全、连接密，最后在附近精找

查询时：从 Layer2 进入 → 一路往下跳 → 在 Layer0 找到最近邻
```

**坑在哪**：很多文章只讲embedding怎么算，不讲索引怎么建。结果就不理解为什么“明明库里有这段话却搜不到”——因为ANN是**近似**的，`efSearch`（HNSW的搜索宽度）调小了，速度快但会漏；调大了，召回全但延迟高。这个权衡是RAG在线检索真实的行为边界，绕不开。

## 四、在线召回：向量负责“意思像”，BM25负责“字对得上”

**打个比方**：向量检索像“懂行的朋友”，你说“手机没电快”，他能给你找来“续航焦虑解决方案”；BM25像“死心眼的检索员”，你搜“iPhone 15 Pro Max”，他严格按这几个词的出现频率和稀有度打分。

问题来了：用户搜“iPhone 15 Pro Max 电池多少毫安”，向量检索可能召回一堆“苹果手机续航评测”（意思相关但没型号），BM25能精确命中带这个型号的那段。**两者各管一段，谁也不能替代谁。**

```
用户Query: "iPhone 15 Pro Max 电池多少毫安"
        │
        ├──► 向量检索 top10:  [续航评测A, 电池技术B, 充电协议C, ...]   ← 语义相关
        │
        └──► BM25  top10:    [型号参数表X, 发布会稿Y, 评测A, ...]     ← 字面精确
                                   │
                                   ▼
                           RRF 融合排序
```

**RRF（倒数排名融合）怎么工作**：不看原始分数（两套分数没法直接比），只看**排名**。某文档在榜单里排第 r 名，就给它 `1/(k+r)` 分（k常取60），两个榜单的分数加起来重排。

```
文档A: 向量榜第1名 → 1/(60+1)=0.0164   BM25榜第3名 → 1/(60+3)=0.0159   合计 0.0323
文档X: 向量榜未上榜→ 0                BM25榜第1名 → 1/(60+1)=0.0164   合计 0.0164
                                                              ↑ A 胜出，因为两路都认它
```

**这个机制的价值**：两路都排前面的文档，说明“意思像”和“字对得上”同时成立，可信度最高。

## 五、重排序：从“分开相亲”到“坐一起聊”

**打个比方**：向量检索用的 **bi-encoder**，是把问题和文档**分开**各自编码成坐标再算距离——像相亲时男女各交一张照片，红娘看照片配不配。速度快（可以提前把所有文档照片拍好），但信息损失大。

**cross-encoder** 是把问题和文档**拼在一起**喂给模型读——像让两人坐下来真聊十分钟，匹配精度高得多，但每来一个新人就得重聊一遍，没法预计算。

```
Bi-encoder（召回阶段，快而粗）:
   Query ──► [模型] ──► 向量q ─┐
                                ├─► 算余弦相似度 → top100
   Doc   ──► [模型] ──► 向量d ─┘

Cross-encoder（重排阶段，慢而准）:
   [Query + Doc 拼成一句话] ──► [模型] ──► 相关性分数 → 重排 top10
```

**为什么这一步不是“玄学开关”**：召回阶段为了速度牺牲了精度，重排阶段用更贵的模型对少量候选做精细判断，把真正相关的顶上去。它是**架构层面的纠偏**，不是调参调出来的运气。工程上通常召回 top50–100，重排后取 top5–10 送进生成。

## 六、Query改写：HyDE是“先编个答案再去搜”

**打个比方**：用户问“报销几天”，这句话太短，和文档里“审核周期为5个工作日”的字面重合度很低。HyDE 的做法是：先让LLM**编一段像答案的话**——“报销一般需要3到5个工作日，视审批层级而定”——然后用这段话的向量去搜。因为这段话的用词和文档更像，更容易搜到。

```
用户短查询: "报销几天"  ──► 向量 ──► 搜不到（太短、口语化）
                │
                ▼ LLM生成假设答案
        "报销一般需要3到5个工作日..."  ──► 向量 ──► 命中"审核周期5个工作日"
```

**“编错了也没关系”这句话要加条件**：HyDE 只要求假设答案的**语义方向对**，不要求事实正确。但如果LLM对这个领域完全不懂，编出来的东西引入了一堆无关术语，向量就会被带偏到错误的区域。**领域越陌生，HyDE越容易帮倒忙。**

---

## 七、生成与拒答：两道闸门，缺一不可

**打个比方**：生成阶段就像开卷考试。你得先规定两件事：第一，**没找到答案的题不许瞎写**（拒答闸门）；第二，**每句话必须能在书上指出来源**（引用约束）。

```
检索结果进入生成前:
        │
        ▼
  ┌─────────────────┐
  │ 相似度 ≥ 阈值？  │──否──► 拒答："知识库中未找到相关信息"
  └────────┬────────┘
           │是
           ▼
  ┌─────────────────┐
  │ 拼Prompt + 约束 │  "仅根据以下资料回答，无法回答时说不知道，并标注来源"
  └────────┬────────┘
           │
           ▼
         生成
```

**为什么拒答不能省**：RAG 降幻觉的前提是“检索到的上下文相关且充分”。如果检索失效、上下文为空，而你没有拒答闸门，模型会对着空气一本正经地编——这时候RAG不但没降幻觉，反而给幻觉披了一层“我有检索”的外衣。

---

## 八、评估：别只看一个总分，要知道断在哪一层

**打个比方**：RAG出问题，可能是“书没找对”（检索层），也可能是“书找对了但答跑偏”（生成层）。只看端到端满意度，就像医生说“你不舒服”但不说哪儿不舒服。

```
                    ┌─ Context Recall：该找的书找到了吗？
        检索层 ─────┤
                    └─ Context Precision：找到的书排在前面吗？

                    ┌─ Faithfulness：答案每句话能在资料里找到依据吗？
        生成层 ─────┤
                    └─ Answer Relevancy：答的是用户问的吗？
```

RAGAS 就是算这四个指标的框架。它的分数是 **LLM当裁判打出来的估计值**，有方差，不是标准答案。行业里常说的“Faithfulness ≥ 0.85”是**某些场景下的经验建议**，不是框架规定，具体得按你的业务风险校准，再配人工抽检。

## 九、一张表收尾：每个环节在干嘛、断在哪

| 环节 | 一句话解释 | 典型断点 |
|---|---|---|
| 解析 | 先看清版面再认字 | 跳过版面分析直接OCR，结构永久丢失 |
| 分块 | 切成能独立看懂的卡片 | 切太碎没上下文，切太大噪声淹关键句 |
| 向量化 | 文字变坐标，意思近的挨着 | 通用模型套垂直领域，相似度不可靠 |
| ANN索引 | 给坐标建分区目录 | 只建向量表不调ANN参数，召回悄悄漏 |
| 混合召回 | 向量管语义，BM25管字面 | 只用向量，型号/代码/条款搜不准 |
| RRF融合 | 看排名不看分数，两榜都认的优先 | 直接拼分数，量纲不同排序失真 |
| 重排序 | 问题文档拼一起精读 | 当成可有可无的开关 |
| HyDE | 先编答案再去搜 | 领域太陌生，编偏了带歪检索 |
| 拒答 | 没证据就闭嘴 | 省掉这步，空上下文变自由发挥 |
| 评估 | 分层定位断点 | 只看总分，不知道修哪 |

**最后一句话**：RAG 的每个组件都在测量某种**信号**（相似度、PPL、排名、相关性分数），但信号不等于结论。PPL高不一定是断层，相似度高不一定是相关，HyDE编的答案也不是永远无害。搞清楚每个信号在什么条件下可信、失效时会在哪一层暴露——这比记住“用哪个方法”重要得多。
